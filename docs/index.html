Detecting and diagnosing faults in a chemical plant

How well can machine learning models spot faults in the Tennessee Eastman Process, and name which fault it is, from a single snapshot of 52 sensor readings? And how quickly can a fault be caught?

Simplified from Downs and Vogel (1993). Numbers are stream numbers.

Two tasks

Process faults can reduce product quality, disrupt operations and create safety risks. An operator needs to know two things, quickly and reliably.

DetectionIs a fault happening right now? A yes-or-no answer from a single 3-minute snapshot of the plant, judged on how many faults it catches against how many false alarms it raises. DiagnosisWhich of the 20 fault types is it? Judged on how well it names every fault, hard ones included (macro-F1), and on which faults it confuses.

Instantaneous measurements only. Every model sees one row at a time: the 52 process variables at a single moment, with no history. That keeps the models simple and comparable, and it is also the main limitation: some faults only show up as slow drifts that a single snapshot can't reveal.

The Tennessee Eastman Process

A realistic simulation of a chemical plant published by Eastman Chemical Company (Downs and Vogel, 1993) and a standard benchmark for process monitoring. Four gaseous reactants (A, C, D, E) react to form two liquid products (G and H) in the five units shown above.

52 variables, recorded every 3 minutes

  • 41 measurements (xmeas_1 to xmeas_41): flows, pressures, levels and temperatures (1 to 22), plus gas compositions from analyzers (23 to 41).
  • 11 manipulated variables (xmv_1 to xmv_11): the valve positions the control system sets.

Labels: when is a row "faulty"?

A faulty run starts out normal; the fault is switched on partway through. Rows before that moment are labelled normal, rows after it faulty. Fault-free runs are normal throughout.

A consequence: faulty rows outnumber normal ones roughly ten to one, so a model that always answers "fault" already scores an F1 of about 0.96. That's why this site reports false alarms and recall on normal operation alongside the usual metrics.

How models are judged

  • Split by simulation run, never by row. Within each fault type, 80% of runs train the models and 20% validate them.
  • Choices are made on validation. Decision thresholds and the best model of each kind are picked using the validation runs only.
  • The test files are used once. The chosen models are retrained on all training runs and evaluated a single time on the separate test files, keeping the thresholds chosen on validation.
  • A common operating point. Detection models are compared at the threshold that gives each one 5% false alarms on normal validation rows.

LearnWhy split by run, not by row?

Samples are only 3 minutes apart, and a chemical plant changes slowly, so neighbouring rows of the same run are nearly identical. If rows were shuffled into training and validation at random, almost every validation row would have a near-copy a few minutes away in the training data. The model could score well just by recognizing that particular run, not by learning what a fault looks like.

Splitting by run keeps every run entirely on one side. Validation then asks the honest question: how does the model do on a run it has never seen? That is the situation a real plant is in.
