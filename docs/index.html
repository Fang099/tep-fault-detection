Detecting and diagnosing faults in a chemical plant

How well can machine learning models spot faults in the Tennessee Eastman Process, and name which fault it is, from a single snapshot of 52 sensor readings? And how quickly can a fault be caught?

Two tasks

Process faults can reduce product quality, disrupt operations and create safety risks. An operator needs to know two things, quickly and reliably.

DetectionIs a fault happening right now? A yes-or-no answer from a single 3-minute snapshot of the plant, judged on how many faults it catches against how many false alarms it raises. DiagnosisWhich of the 20 fault types is it? Judged on how well it names every fault, hard ones included (macro-F1), and on which faults it confuses.

Instantaneous measurements only. Every model sees one row at a time: the 52 process variables at a single moment, with no history. That keeps the models simple and comparable, and it is also the main limitation: some faults only show up as slow drifts that a single snapshot can't reveal.

The Tennessee Eastman Process

A realistic simulation of a chemical plant published by Eastman Chemical Company (Downs and Vogel, 1993) and a standard benchmark for process monitoring. Four gaseous reactants (A, C, D, E) react to form two liquid products (G and H) in the five units shown above.

52 variables, recorded every 3 minutes

  • 41 measurements (xmeas_1 to xmeas_41): flows, pressures, levels and temperatures (1 to 22), plus gas compositions from analyzers (23 to 41).
  • 11 manipulated variables (xmv_1 to xmv_11): the valve positions the control system sets.

Data quality

A fault, sensor by sensor (mean shift and variance ratio)

Pick a fault. Its sensors are listed by how much the fault changes them, in two ways. Mean shift: how far the sensor's average after the fault moves from its normal average, in standard deviations of normal operation (σ). Spread vs normal: how much more (or less) the sensor fluctuates after the fault, as the ratio of its standard deviation to the normal one; ×1 is unchanged, ×3 means it swings three times as much.

Labels: when is a row "faulty"? (target labels)

A faulty run starts out normal; the fault is switched on partway through. Rows before that moment are labelled normal, rows after it faulty. Fault-free runs are normal throughout.

A consequence: faulty rows outnumber normal ones roughly ten to one, so a model that always answers "fault" already scores an F1 of about 0.96. That's why this site reports false alarms and recall on normal operation alongside the usual metrics.

How models are judged (validation protocol)

  • Split by run, never by row. Of the training runs of each fault type (and of the fault-free runs), 80% are used to train the models and 20% to validate them. A run always stays whole on one side, and a run number goes to the same side for every fault type (why: see below).
  • Choices are made on validation. Decision thresholds and the best model of each kind are picked using the validation runs only.
  • The test files are used once. The chosen models are retrained on all training runs and evaluated a single time on the separate test files, keeping the thresholds chosen on validation.
  • A common operating point. Detection models are compared at the threshold that gives each one 5% false alarms on normal validation rows.

LearnWhy split by run, not by row?

Samples are only 3 minutes apart, and a chemical plant changes slowly, so neighbouring rows of the same run are nearly identical. If rows were shuffled into training and validation at random, almost every validation row would have a near-copy a few minutes away in the training data. A model could then score higher than it deserves, by recognizing that particular run rather than learning what a fault looks like. How much higher depends on the model: the measurement below shows it.

Splitting by run keeps every run entirely on one side. Validation then asks the honest question: how does the model do on a run it has never seen? That is the situation a real plant is in.

There is a second, less obvious trap in this dataset. Run 7 of every fault type is the same simulation as fault-free run 7 (same starting state, same random disturbances), with the fault switched on after one hour (sample 20). So the first 20 rows of all 21 versions of run 7 are identical to the last decimal, and they stay identical until the fault starts to show.

Why that matters, even though those rows contain no fault: if fault-free run 7 and fault 5's run 7 were in training while fault 3's run 7 were in validation, then

  • its first rows would be rows the model was trained on, so it scores them with unearned confidence. These are exactly the normal rows used to set the 5% false-alarm threshold, so the threshold would be tuned on memorized rows;
  • after the fault starts, the run still carries run 7's disturbances. For a fault that barely changes the plant (3, 9 or 15), the whole run stays almost a copy of fault-free run 7, so validation would partly be re-scoring training data.

Either way the validation score would no longer answer "how does the model do on a run it has never seen?". So the split is made on the run number: all 21 versions of run 7 go to the same side. The pipeline counts the validation rows that exactly match a training row; the count is in the data quality checks above (it is 0).

  • Explored the data and tried simple ML models on my own first, to understand the data and the problem before bringing in AI.
  • Worked out that the data has to be split by simulation run, not by row.
  • Decided which model families to compare and which experiments to run, among them training on all the data, the learning curve on both axes, the single 21-label model as an alternative to the two-stage chain, PCA monitoring with history inputs, the RBF SVM on a subset, the random-split demonstration and which sensors matter.
  • Ran all training, validation and the final test on my own and the lab's computers, and handled the practical problems along the way (memory limits, interrupted runs, choosing which slow models to skip).
  • Reviewed the code and the explanations, asked for corrections where something was unclear or wrong, and tested the website page by page.

What Claude did

  • Designed most of the website's layout.
  • Wrote most of the explanatory text on the site and the documentation of the pipeline.
  • Proposed parts of the method that I then accepted, such as choosing thresholds at a fixed 5% false alarm rate on validation only, and bootstrap intervals over runs.

What AI did not do

How the work was checked

  • Leakage: the pipeline counts validation and test rows that exactly match a training row (0 in both).
